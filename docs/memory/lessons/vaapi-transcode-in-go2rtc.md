# VAAPI transcoding inside go2rtc

Read when: changing the `desk` stream, the `ffmpeg:` templates in `relay/go2rtc.yaml`, the GPU passthrough, the `feed` stream's sources, or when the Desk display gets audio but no video or the kernel logs GPU hangs.
Status: verified
Scope: Relay image (Alpine 3.23, ffmpeg 8.0.1, go2rtc 1.9.14) on a Radeon 780M (Mesa radeonsi 25.2.7) and an Intel UHD 770 (iHD 25.4.6)
Verified: 2026-10-28
Source: test container on the Radeon on 2026-09-27; test containers on both GPUs on 2026-10-27, running the `desk` templates on a synthetic 4K HEVC clip; the production Relay and a full test Relay on the UHD 770 on 2026-10-28; go2rtc source (`pkg/rtsp/producer.go`, `internal/streams/producer.go`, `internal/ffmpeg/ffmpeg.go`, `hardware/hardware.go`)
Recheck when: go2rtc, ffmpeg, Alpine, the media driver, or the GPU changes, or the `feed` or `desk` sources change.

- **Symptom:** `/api/stream.mp4?src=desk` returns audio only. go2rtc logs nothing, because it starts ffmpeg with `-v error` and silently skips a source that fails. Run the ffmpeg command by hand inside the container to see the error.
- **`hwupload` needs a named device.** With `-hwaccel vaapi` alone, ffmpeg 8 fails with "A hardware device reference is required to upload frames to." Declare it with `-init_hw_device vaapi=gpu:/dev/dri/renderD128 -filter_hw_device gpu -hwaccel_device gpu`.
- **Don't combine `#raw=-vf …` with `#width`, `#height`, or `#hardware`.** go2rtc writes its own `-vf` last, and ffmpeg keeps the last one, so yours is silently dropped. Put the whole filter chain and encoder settings in a custom `#video=` template, and the hwaccel flags in a custom `#input=` template.
- **Re-time with `setpts=N/(25*TB)` plus `-r 25`.** Without it, ffmpeg's constant-frame-rate logic repeats the keyframe about 6 times after each Keyframe stall and then drops the burst behind it.
- **Measured:** 4K HEVC to 1080p H.264 runs at a steady 25 fps and adds about 1–20 ms beyond the source. `-async_depth 1` and `-bf 0` keep the encoder from holding frames.
- **The `desk` ffmpeg must ask for audio too (`#query=audio`).** go2rtc sets up only the tracks its first consumers ask for. When a later consumer asks a playing RTSP source for another track, go2rtc reconnects to add it (`GetTrack` → `Reconnect` in `pkg/rtsp/producer.go`), and the receivers already attached carry on with the new session's packets. The `desk` ffmpeg asked `feed` for video only, and the `desk` stream's audio source asked for the audio about 1 ms after ffmpeg's first output. The HEVC decoder then got the new session's frames, from mid-GOP, spliced onto the old one's, with references that pointed at the wrong pictures. On the UHD 770 (i915, iHD 25.4.6) the video engine hung within a few frames: the kernel logged `Resetting vcs0 for preemption time out` (or `stopped heartbeat` with forced preemption off) and `GPU HANG: ecode 12:4:28fffffd` in ffmpeg's `dec0:0:hevc`. go2rtc restarted ffmpeg each time the Desk display reconnected, and it hung again, for a minute or more after every Relay start. Intel says its HEVC hardware decoder can't decode frames whose references are missing; the Radeon tolerated the splice. A file replay of the same stream, ffmpeg started by hand, and other flags didn't reproduce it. Removing the audio source did, and so does `#query=audio`, which makes ffmpeg's input `feed?video&audio`: go2rtc sets up both tracks before PLAY, and ffmpeg still gets `-an`. On a full test Relay it gave 0 hangs in 4 fresh starts, 3 starts with an audio consumer joining mid-stream, and 3 starts behind a video-only viewer, against 4 hangs in 4 starts without it. To reproduce: run the image with the stream env, fetch `/api/stream.mp4?src=desk` for 5 s a few times, and count `GPU HANG` in `dmesg`. A stalled start delivers about 200 KB, a good one about 2.5 MB.
- **One image serves both GPUs.** libva loads radeonsi on an AMD GPU and iHD on an Intel one, and both encode through `VAEntrypointEncSlice`, so the templates need no change between them. Each converts 200 frames of 4K HEVC to 1080p H.264 in about a second.
- **Image size:** the AMD driver (`mesa-va-gallium`) pulls in LLVM, which takes the image from about 226 MB to about 528 MB, and the Intel driver (`intel-media-driver`) adds about 54 MB more, to 582 MB. There's no lighter radeonsi VAAPI build on Alpine, so dropping the AMD driver is the way to shrink the image once no host needs it.
